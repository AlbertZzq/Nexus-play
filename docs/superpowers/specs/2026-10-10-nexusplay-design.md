## 3. 架构选择

采用一套 Vite + React + TypeScript 应用，React Router 管理路由，现代 CSS 和 CSS 变量管理样式。共享页面内容组件、筛选函数和本地数据，分别使用 `TopNavigationLayout` 与 `SidebarLayout` 展示。

选择此方案的理由是数据与行为只有一套，能够直接测试两种设计的等价性；布局仍可有明显差异。两个独立应用会重复页面逻辑，容易产生功能漂移。仅更换背景颜色的单布局方案无法体现提案要求的导航和密度差异，因此不采用。

不增加 Redux、后端、数据库、大型 UI 框架或在线服务层。使用 React 局部状态与 URL 参数即可完成需求。

建议的职责划分：

| 位置 | 职责 |
| --- | --- |
| `src/app/` | 路由、设计选择、共享应用状态入口 |
| `src/layouts/` | 顶部导航布局与侧栏布局 |
| `src/pages/` | 十类页面的共享内容与交互 |
| `src/components/` | 导航、设计切换、游戏卡片、评分、筛选、内容卡片、空状态 |
| `src/data/` | 集中定义类型与确定性的本地内容 |
| `src/utils/` | 游戏筛选、排序、价格及日期格式化等明确需要的纯函数 |
| `src/styles/` | 基础样式、设计变量、布局及响应式规则 |
| `public/assets/` | 本地图片及必要的来源说明 |
| `docs/` | 规格、实施计划和验收记录 |

页面组件不因当前设计而选择不同的数据。布局和 CSS 可以调整网格列数、排列方式、过滤面板位置及间距，但不能改变结果条目或默认排序。

## 4. 信息架构与十类页面

顶级结构保持 Home、Games、Content、Community、Deals。Games 下包含 Discover、Game Details、Platforms、Release Calendar；Content 下包含 News、Reviews、Guides。Game Details 从游戏卡片进入，不设置缺少游戏上下文的独立主菜单入口。

| 页面类型与路由 | 必须显示的内容 | 必须工作的交互 |
| --- | --- | --- |
| Home `/` | 精选游戏、Trending Now、Top Rated by Players、最新新闻、热门攻略、优惠、发售预览、社区摘要 | 精选与游戏卡片进入详情，各分区进入对应页面 |
| Discover `/discover` | 结果数量、游戏图片、名称、平台、类型、玩家评分、发售信息 | 标题搜索；类型、平台、最低玩家评分、发售年份筛选；按玩家评分、热度、发售日期、名称排序；重置和无结果状态 |
| Game Details `/games/:slug` | 标题、图片、简介、类型、平台、发售信息、突出玩家评分、次要媒体分数、截图、玩家评论、攻略、优惠、相似游戏 | 返回浏览列表、相关游戏链接、攻略展开、愿望单切换 |
| News `/news` | 图片、标题、日期、摘要；Industry、Updates、Esports、Releases 分类 | All 与分类筛选；有阅读入口的故事可在当前页展开正文 |
| Guides `/guides` | 关联游戏、标题、攻略类型、难度、更新时间和摘要 | 按游戏和类型筛选；在当前页展开有实际内容的攻略 |
| Community `/community` | 精选玩家评论、按游戏标识的讨论、回复及浏览量样本、热门话题 | 游戏筛选及只读话题内容展开；关联游戏链接 |
| Deals `/deals` | 游戏、平台、商店、原价、现价、折扣与样本状态 | 平台、商店、最低折扣筛选；20%+、50%+、75%+；重置与无结果状态 |
| Reviews `/reviews` | 排名、游戏、玩家评分、评分人数、推荐比例、评论摘要；次要媒体分数和热度 | 游戏链接；评分字段与排序在两种设计中相同 |
| Release Calendar `/calendar` | 按月分组的示例发售列表、游戏、日期、平台及类型 | All、PC、PlayStation、Xbox、Nintendo 筛选；游戏链接 |
| Platforms `/platforms` | PC、PlayStation、Xbox、Nintendo 分区；热门、高评分、发售预览 | 平台选择改变三个分区的内容；游戏链接 |

文章、攻略、讨论使用页面内展开区，不增加顶级页面类型。未知路由或不存在的游戏提供简洁的未找到状态及返回入口，这是导航容错，不是第十一类内容页面。

愿望单仅为详情页的本机保存状态，用 localStorage 保存游戏 ID，不增加账号、同步服务或愿望单独立页面。该功能来自原提案，并已在设计方向确认中保留。

## 5. 两套视觉设计

| 维度 | Design 1 | Design 2 |
| --- | --- | --- |
| 主导航 | 深色顶部横向导航，按既定信息架构分组 | 桌面端固定深色左侧导航，同样的分组和目的地 |
| 主背景 | 深海军蓝，较浅的深色面板 | 淡灰背景、白色内容面板 |
| 内容密度 | 紧凑，较小卡片、短间距、更多并列内容 | 更大卡片、较大间距、清楚分区 |
| Discover | 结果左侧的筛选栏 | 结果上方的筛选面板 |
| Reviews | 紧凑的比较表格或行式排列 | 更高的评分行与更宽松的信息间距 |
| Calendar | 紧凑月份分组列表 | 月份分隔更明显的时间线式列表 |
| 强调色 | 克制的蓝色，清楚的评分语义色 | 对应蓝色强调和相同的评分含义 |

两套设计都使用易读的系统无衬线字体、本地图片、适度圆角和清晰边界。初始间距参考：Design 1 分区约 24px、卡片间约 12px；Design 2 分区约 40px、卡片间约 24px。桌面侧栏约 224px，实际尺寸在视觉验收中调整，不通过固定高度裁切内容。

首页的精选区只占合理高度，首屏仍能看到实用游戏内容。避免霓虹发光、大面积渐变、装饰性玻璃效果、夸张字体和无功能按钮。玩家评分始终比媒体分数更突出。

## 6. 路由、状态与设计切换

- 提供持续可见但不抢占主体的 `Design 1 — Top Navigation` 和 `Design 2 — Left Navigation` 切换控件。
- 支持 `?design=1`、`?design=2`。有效的 URL 选择优先于本机偏好；缺省读取本机偏好，再缺省为 Design 1。
- 切换只更新设计参数与本机偏好，不清空当前路径、筛选参数或搜索内容。共用页面状态不因外层布局更换而丢失。
- Discover 搜索及筛选使用明确的 URL 参数，例如 `q`、`genre`、`platform`、`rating`、`year`、`sort`。其他列表页按需要使用 `category`、`game`、`type`、`store`、`discount` 等参数。
- 导航保留设计选择；页面特有筛选仅属于相应页面，不污染不相关页面。浏览器前进、后退和刷新应重现当前 URL 对应状态。
- 全站搜索明确为游戏标题搜索，提交后进入 Discover 并保留设计选择，不暗示已实现全文搜索。
- 未知筛选值退回该控件默认值；不存在的游戏不导致运行时崩溃。
- localStorage 不可用时，浏览和设计切换继续工作，仅不跨刷新保存本机偏好与愿望单。

## 7. 数据、图片与内容真实性

本地集中数据至少覆盖 16 款可识别游戏、四个平台、多种类型及不同评分和发售年份，保证筛选与排序有可展示的差异。每款游戏具有稳定 ID/slug、名称、简介、平台、类型、日期、玩家评分、媒体分数、评分人数、推荐比例、热度和图片引用；热度为示例指标，不冒充实时在线人数。

新闻覆盖四个指定分类，每类至少两条。攻略覆盖 Beginner、Build、Boss、Farming/Progression、Collectibles 等适用类型。评论、讨论、优惠和发售条目通过游戏 ID 关联，避免复制游戏标题及对象造成不一致。

优惠用同一币种 USD，金额以最小货币单位存储，折扣由原价和现价计算，保持显示一致。所有分数、价格、人数、讨论、新闻与发售日期按教学样本处理。页面持续提供简短的 `Class prototype · Illustrative data` 提示；优惠与日历另外明确价格及日期为样本，不按机器当前日期动态隐藏课堂数据。

每个可路由游戏有完整的基本详情。关联攻略或优惠不存在时显示明确的无相关内容说明，不伪造关系。示例内容不得使用 lorem ipsum，不将合成评论署名为真实个人。

图片保存在项目内，演示不依赖外链加载。实现时优先使用可合法复用且来源明确的游戏宣传图片；记录来源、许可或使用限制，不批量复制参考网站资源。没有合适素材时使用本地原创的游戏标题视觉图，并明确其为原型插图，不冒称实际游戏截图。详情媒体区同样区分真实截图与原型插图。图片尺寸固定比例，提供合适的替代文字。

参考开源项目仅可用于理解架构思路，不能复制源码或设计。此原型不需要外部游戏 API。

## 8. 响应式与可访问性

- 重点验收 1440px 和 1920px，并检查 1024px、768px；额外做一次约 390px 的基本可用性检查。
- Design 1 在宽度不足时将导航收拢为可键盘操作的菜单。Design 2 在桌面保持侧栏，在约 1024px 以下改为可展开导航，内容不被固定侧栏挤出屏幕。
- 菜单按钮具备可访问名称、`aria-expanded` 和正确焦点表现；Escape 可关闭，选择目的地后收起。
- 使用语义化 header、nav、main、section，提供跳至主要内容入口；每页有唯一清晰的主标题。
- 表单控件有可见标签，当前导航及分类状态不只依赖颜色；键盘焦点始终可见。
- 正文对比度至少 4.5:1，大字与重要界面边界按相应可访问性标准检查。
- 网格、比较行、长标题和筛选栏自动换行；不产生未说明的横向滚动，不通过全局隐藏溢出掩盖布局问题。
- 页面内展开内容可用原生 details/summary 或同等可访问实现，避免为简单内容引入复杂模态框系统。

## 9. 范围边界

不实现登录、注册、个人资料、发帖、消息、论坛后端、购物车、结账、支付、管理后台、AI 推荐、数据库或云端服务。相似游戏只是依据本地类型/平台关联的确定性列表。

优惠是信息展示，不提供购买流程。若展示商店入口，只链接明确的商店公开页面并标注外部链接，不承诺样本价格有效；没有可靠目的地时不展示无作用的购买按钮。

原型不声称游戏数据实时更新、不声称用户偏好已经过研究验证，也不额外建设 CMS 或内容编辑系统。

## 10. 验证与完成标准

实施采用 Vitest + React Testing Library 验证用户可观察行为，使用可用的浏览器工具做真实页面交互和视觉检查。实现时采用测试先行：先写关键失败用例，确认失败原因，再实现通过；不为静态样式编写重复实现细节的测试。

自动化覆盖至少包括：

1. 十类页面在两套设计中全部可渲染，并显示相同核心标题、游戏条目和内容。
2. 设计切换改变导航及布局，保持当前路径、搜索、筛选、排序与结果；URL、本机偏好及浏览器历史符合规则。
3. 标题搜索忽略大小写，支持清空；无匹配时显示有用的空状态与重置入口。
4. 类型、平台、最低评分、年份可组合筛选；四种排序产生预期顺序，相同值保持确定性。
5. 点击游戏卡片到正确详情页；未知 slug 有返回入口。
6. 新闻分类、攻略筛选、优惠筛选、日历和平台选择真正改变相应结果，且设计间一致。
7. 本机愿望单切换与持久化可用；缺少本机存储时主要浏览仍可用。
8. 数据关系无失效游戏引用，所需图片路径存在，优惠折扣与金额一致。

最终必须实际执行仓库配置的 lint、完整测试、TypeScript 检查及生产构建。预计脚本为 `npm run lint`、`npm test -- --run`、`npm run build`，以实施后 package.json 的实际定义为准。本规格不代表这些命令已经运行或通过。

浏览器验收必须覆盖两套设计的全部十类页面，重点截图检查 Home、Discover、Game Details；其余页面也必须实际查看。测试导航、切换、搜索、组合筛选、重置、空状态和小屏菜单。检查控制台错误、破损图片、溢出、文字裁切、颜色对比及无作用控件。截图和验收记录保存到本项目 F 盘目录，记录真实尺寸与结果；修复后复查受影响页面。

完成条件是上述行为、检查和文档全部交付，并完成主要实现的独立代码审查。任何未完成或受环境限制的验证必须如实列出，不以“应该通过”替代运行结果。
